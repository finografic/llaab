## Decisions made

- **P1e `cloud`, run at Opus.** Justin's explicit instruction was to run P1d through P1g on Opus before switching models for the app-build phases, so this bank was not written at Sonnet as originally planned. The difficulty-3 items in this domain are all "why the mapping is imperfect" questions, where the distractor has to be a true statement about the other cloud, so distractor quality was the deciding factor same as `typescript`.
- **P1e `cloud`.** Exemplar E5 in the spec is itself a `cloud` glossary question, so it was included in the bank verbatim, matching the calls for E1 (`apis`), E2 (`testing`), E4 (`platform`) and E6 (`typescript`). **Its id did not need renumbering:** the glossary was ordered so E5 lands in sixth position and keeps its original `cloud-006`. Stem, options, `distractorNotes` and `explanation` are verbatim. A `stemSpoken` and an `explanationSpoken` were added, because the text contains AWS, KMS and ACM plus a hyphenated "checked-in credential", none of which should reach kokoro in that form.
- **P1e `cloud`.** 34 questions, split 11 glossary / 23 depth, 24 mcq / 10 order (70.6% mcq). Both sections sit at the top of the spec's soft bands rather than outside either. Difficulty is 11 at level 1, 13 at level 2, 10 at level 3.
- **P1e `cloud`. Mapping is over-weighted deliberately, per the phase brief.** 12 of 34 questions are AWS-to-Azure mapping questions. **Eight of those are explicitly about where the mapping is imperfect**, against a spec floor of three: `cloud-010` (S3 to Blob, storage account and blob types), `cloud-012` (Lambda to Functions, the always-on hosting plans have no Lambda equivalent), `cloud-013` (CloudWatch to App Insights, APM spans CloudWatch plus X-Ray plus real user monitoring, with Azure Monitor as the umbrella), `cloud-014` (IAM to Entra ID, Azure splits identity from Azure RBAC and adds a scope hierarchy), `cloud-015` (SQS to Service Bus, the AWS shape spans SQS plus SNS plus EventBridge), `cloud-016` (RDS to Azure SQL Database, engine host versus platform database, with Managed Instance as the nearer lift and shift), `cloud-017` (Terraform to Bicep, the state file versus ARM holding state), `cloud-018` (CloudFront to Front Door, Azure merges caching, routing and firewall where AWS splits them). E5 itself (`cloud-006`) carries the same calibration in its explanation, so the imperfect-mapping set is arguably nine.
- **P1e `cloud`. Service Bus and MassTransit kept light, as instructed.** Three questions touch messaging and none of them is a distributed-systems question: `cloud-011` (what a bus is for), `cloud-015` (topics and subscriptions versus a plain queue), `cloud-022` (what publish and subscribe costs you). MassTransit appears only as a named library inside one explanation, exactly as the glossary source describes it. No delivery-semantics, saga, outbox or ordering-guarantee questions were written.
- **P1e `cloud`. Two questions are rehearsal rather than knowledge, and that is intentional.** `cloud-020` (mcq, difficulty 3) and `cloud-034` (order, difficulty 3) both drill the "I have not worked in Azure" answer itself: honesty first, then the transferable model, then the mapping, then where the mapping stops. The spec's D3 brief names holding a real conversation as the goal, and the prep doc's mindset section says the honest answer reads as senior, so the skill is worth practising directly rather than only implying it.
- **P1e `cloud`. No `code` blocks.** The schema allows `hcl` and `yaml`, and a Bicep or Terraform snippet was considered and dropped: Justin's IaC exposure is the AWS/Terraform demo, so a Bicep snippet would test syntax recall he does not have and the spec bans framework-syntax trivia. The Terraform-versus-Bicep question (`cloud-017`) asks about state and the plan step, which is the part that transfers.
- **P1e `cloud`. Two current-Azure facts were web-verified rather than written from memory**, since a stale fact would be memorised as correct (spec section 7). Confirmed against Microsoft Learn: the classic Azure CDN and classic Front Door products are being retired in favour of Azure Front Door Standard/Premium, so `cloud-018` treats Front Door as the current CloudFront equivalent and uses "classic CDN is still the default" as a distractor that was right a few years ago. Azure Blob access tiers are Hot, Cool, Cold and Archive in that order of storage cost (`cloud-030`). Nothing else needed a lookup. Azure Cognitive Search was deliberately **not** used in any question, because it has been renamed Azure AI Search and the source prep doc still uses the old name; a question hinging on it would teach whichever name turns out to be wrong on Friday.
- **P1e `cloud`.** `distractorNotes` are filled on all six difficulty-3 MCQs as the spec requires, plus five difficulty-2 MCQs and two difficulty-1 MCQs where a near-miss option needed naming. Ordering questions carry `orderRationale` instead, per the schema.
- **P1e `cloud`.** `stemSpoken` / `explanationSpoken` added only where TTS would mangle the text, not blanket-applied: the letter acronyms (S3, EC2, AWS, RDS, IAM, SQS, SNS, SQL, HTTP, KMS, ACM), the camel-case product names (CloudWatch, CloudTrail, CloudFront, DynamoDB, MassTransit), X-Ray, Entra ID, and "real user monitoring" written out in place of RUM. `vCores` was written as "virtual cores" in the spoken variant.
- **P1e `cloud`.** The markdown study doc is generated from the JSON, same as the other banks, so the two cannot drift. Format follows `typescript.md` and `apis.md` (no `Items:` line, no `_Tags:_` line), which is the most recent convention; `testing.md` still carries an `Items:` line and `vald.md` still carries tags, and neither was retrofitted since this phase does not own those files.

Reason: `vald` is the one bank whose content cannot be produced from general training knowledge. It needs niche, employer-specific product facts (device names, what HumanTrak actually is, what Hub and Norms are) read carefully out of the source documents, so accuracy depends on grounded reading rather than domain fluency. `cloud` and `frontend` are general-knowledge domains and are safer to run later or at a smaller model.

Difficulty is 11 at level 1 and 3 at level 2 (`vald-009` device/Hub responsibility split, `vald-013` observability tooling, `vald-014` MassTransit), with no level 3, since the spec calls this a warm-up rather than a judgement domain. `distractorNotes` is therefore unused; each explanation names the tempting distractor inline instead, which is the spec's stated purpose for that field.
- **P1g `vald`. Source coverage is thinner than the phase brief assumed, and this is the one real finding.** The three source documents name six devices (ForceDecks, NordBord, ForceFrame, DynaMo, HumanTrak, SmartSpeed) in a single list, but they only ever describe those devices collectively as "hardware that measures human movement". **No source document states what any individual device measures**, with the single exception of HumanTrak (3D markerless motion tracking, 20 plus assessments, real time feedback).
